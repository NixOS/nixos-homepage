I have shown based on an idea by Tom Berek that it is possible to enable custom nix language evaluators as part of the regular nix CLI frontend by using a new experimental feature called dynamic derivations.
This gives competing implementations a more level playing field with the built-in evaluator, opening up avenues for broader performance gains and experimentation within the community.
It also enables evaluation to be done as a remote build, opening up opportunities to be flexible with where CPU or memory heavy evaluations are run.

## The Technical Model

Evaluation of `flake.nix` code is possible within the build sandbox without `recursive-nix`.
A limited daemon RPC socket is opened in the sandbox which accepts store additions (sources and `.drv` files, such as generated by `nix eval` or `nix-instantiate`) and the submission of the build's output, but no queries of the outer store.
It accepts the `AddToStore` family of daemon protocol operations (`AddToStore`, `AddMultipleToStore`, `AddToStoreNar`, `AddToStoreScanning`) and `SubmitOutput`, plus `AddTempRoot` and `IsValidPath` for the CLI's own use.
The evaluator writes its derivation graph into a private store inside the sandbox; the builder then re-adds that graph through the socket in one `AddMultipleToStore` (the whole closure in dependency order on one connection) and submits the top-level derivation with `nix store submit-output`.

## Sandboxed Evaluation

When tested on a large flake (15GB of inputs), the sandboxed evaluation adds no cost once inputs arrive as store paths: the evaluation itself takes 6.4–7.4s inside the sandbox vs 8.4–9.7s native.
End-to-end time for sandboxed vs non-sandboxed with a cold store is 8.0s vs 8.5s for the smallest target (1,065 derivations and sources handed back through the socket) and 8.7–9.2s vs 8.9–9.4s for the two larger ones (2,252 and 2,064 objects); the overhead for the dynamic derivation case is the re-add of the resulting graph into the outer store in one `AddMultipleToStore` (0.4–1.5s), not the evaluation.
With warm stores nothing changes on either side: 7.8s / 9.1s / 9.4s sandboxed vs 8.7s / 9.7s / 8.4s native.

In the tables below, cold is the first planner build, warm is a second build right after with a fresh salt, and both are the whole planner build (registration, evaluation, re-add, submit) with the evaluation alone in parentheses.
The outside-sandbox baseline is the same evaluator evaluating the same thing natively on the same machine, first run / second run. Every sandboxed run emitted the identical derivation path to its baseline.

## Remote Building

A proof of concept was demonstrated as a text-hashed, content-addressed derivation whose builder runs `nix-instantiate` in a private store inside the sandbox, hands the resulting graph back through the socket and emits the resulting `.drv` as its output.
A consumer depends on it through `builtins.outputOf`, so the target expression is never evaluated outside a build. Needs the `ca-derivations` + `dynamic-derivations` experimental features enabled.
Experiment performed on `hello`.
Remote evaluation with a cold store was 4.7s (1.1s client eval + 3.6s remote planner build, 12 paths copied to the worker; a worker that has never seen the evaluator and nixpkgs closures first copies about 345 paths, which took 10s in an earlier run), warm store was 3.6s (1.1s client eval + 2.5s remote build; the graph lands in the worker's store, so there is no copy-back), and native on the worker is 0.42s cold and 0.30s warm.

## Granular Evaluation Caching

The planner is content-addressed, so an evaluation result is cached like any build result: rebuilding an unchanged planner is a realisation lookup, not an evaluation.
With only the files the target's evaluation reads as the planner's input, a change anywhere else in the tree leaves the cache key untouched.

### Large Flake Granular Caching

Each cell is the whole `nix build` of the planner for target C; "hit" means the realisation was found and nothing was evaluated.
Native `nix eval` of the same target with the same pinned inputs: 9.6s cold, then 5.7s, 7.1s after the unrelated change and 6.1s after that.

| scenario                                       | full-tree planner                | fragment planner                    |
| ---------------------------------------------- | -------------------------------- | ----------------------------------- |
| first build                                    | 9.2 s (eval 6.7 s, re-add 1.5 s) | 9.3 s (eval 6.8 s, re-add 1.5 s)    |
| rebuilt, nothing changed                       | 0.4 s, hit                       | 0.4 s, hit                          |
| unrelated change (a file no evaluation reads)  | 9.3 s, re-evaluated              | 0.4 s, hit                          |
| change inside the fragment (a shared Nix file) | 9.4 s, re-evaluated              | 9.9 s, re-evaluated                 |
| second target (B) after the target C change    | —                                | 0.4 s, hit (its first build: 8.5 s) |

### Large Flake Granular Caching, 447 Targets

447 targets of the large flake, each with its own fragment planner; every planner set is built by one `nix build` with 16 parallel builds, and "hit" means no evaluation ran.
Native is one `nix eval` of all 447 targets' derivation paths with the same pinned inputs.
Change 1 is a host configuration file that only one documentation target reads (that target's own evaluation takes 153 s); change 2 is a source file of one small tool.

|                                           | first build             | rebuilt, nothing changed | after change 1                  | after change 2                 |
| ----------------------------------------- | ----------------------- | ------------------------ | ------------------------------- | ------------------------------ |
| native, all 447 targets in one evaluation | 252.9 s                 | 257.0 s                  | 247.1 s                         | 249.6 s                        |
| 447 full-tree planners                    | 668.0 s (447 evaluated) | 7.0 s (447 hits)         | 760.0 s (447 evaluated)         | 491.8 s (447 evaluated)        |
| 447 fragment planners                     | 567.3 s (447 evaluated) | 6.4 s (447 hits)         | 157.3 s (1 evaluated, 446 hits) | 14.6 s (1 evaluated, 446 hits) |
